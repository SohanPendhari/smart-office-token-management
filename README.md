# Smart Office Queue & Token Management System

A visitor picks an office department, gets a token such as `IT-021`, watches their queue position and estimated waiting time update live, and is called by staff. Staff and admins run the whole queue from the same **Flutter web app** (runs in Chrome; the same code can also build for Android).

> **Flutter is the presentation layer. Go owns every business rule. PostgreSQL is the source of truth.**
> The app never decides which token is next, never generates a token number, and never enforces priority / no-show / pause rules. It only asks the backend.

---

## 1. Project Overview

| Role | Can do |
|------|--------|
| **Visitor** (no account) | Select department, generate token, see queue position + estimated wait + live queue, cancel a waiting token |
| **Staff** (one department) | Login, dashboard, call next, complete, no-show, transfer, set priority, pause / resume **their** department |
| **Admin** | Everything staff can do, in **every** department |

## 2. Features

- Four separate department queues (IT Support, HR, Accounts, Administration)
- Backend-generated, unique, per-day token numbers (`IT-001`, `IT-002`, ...)
- Priority queue that never interrupts the token being served
- No-show handling: first -> end of queue, second -> cancelled
- Transfer between departments with full history
- Pause / resume a department (existing tokens continue, new ones are blocked)
- Queue position and estimated wait that update as the queue moves (REST polling every 5 s)
- Concurrency-safe **Call Next** (`SELECT ... FOR UPDATE SKIP LOCKED`)
- JWT staff authentication, bcrypt password hashes, role + department authorization
- Dashboard: waiting, serving, completed, no-shows, average waiting / service time, per-department counts
- Audit trail (`token_events`) and statistics (`token_service_sessions`, `daily_queue_stats`)
- **Desktop-friendly UI:** responsive layouts from phone to wide monitor; visitors get a landing page with top navigation, staff get a sidebar console (Dashboard + one page per department) with a details dialog for each token
- API URL changeable inside the app (same PC, another device on the Wi-Fi, or Android emulator)

## 3. Technology Stack

| Layer | Technology |
|-------|------------|
| Frontend | **Flutter Web** (Chrome / any browser), Riverpod 2, `http`, `shared_preferences` |
| Backend | Go 1.22+, **standard library `net/http`** (method + path routing), `database/sql` + `lib/pq`, `golang-jwt/jwt/v5`, `bcrypt` |
| Database | PostgreSQL 14+ |

## 4. Architecture

```
 Flutter web app  --REST/JSON-->  Go backend  --SQL / TX-->  PostgreSQL
 (screens, Riverpod)                  handlers -> services -> repositories
```

Backend layers: `handlers` (HTTP only) -> `services` (all rules, owns transactions) -> `repositories` (all SQL). `middleware` = JWT auth, logging, CORS, panic recovery.

## 14. Queue Logic

Call-next order is decided in one place - the backend (`LockNextWaiting`):

```sql
SELECT id FROM tokens
WHERE department_id = $1 AND status = 'WAITING'
ORDER BY priority DESC, priority_level DESC, sequence_number ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```
Result: priority + oldest -> priority + next -> normal + oldest -> normal + next.

- **Concurrency.** Call Next runs in a transaction. `FOR UPDATE SKIP LOCKED` means two staff pressing it at the same instant lock *different* rows - never the same token, and nobody blocks. (Verified by the smoke test with two simultaneous staff, repeated rounds.)
- **Unique token numbers.** `queue_settings.token_counter` is incremented with a row-locking `UPDATE ... RETURNING`; concurrent generations are serialised. The counter restarts each day. A `UNIQUE (token_number, created_date)` constraint is the safety net.
- **Estimated wait** = `people ahead x average service time / active counters` (rounded up). Average service time = mean of the last 20 completed services of that department, falling back to `queue_settings.avg_service_minutes` (5) until 5 samples exist, and never below 1 minute. Position = people ahead + 1.
- A staff member **cannot call the next token while still serving one** (409) - a serving token is never interrupted.
- A visitor cannot hold two active tokens for the same department with one mobile number.

## 15. No-Show Logic

Only a token that is being served can be marked no-show.

| Occurrence | Result |
|------------|--------|
| 1st (`no_show_count` = 0 -> 1) | `status = WAITING`, **new** `sequence_number` -> moves to the **end** of the queue (a priority flag is dropped so it really goes to the end) |
| 2nd (`no_show_count` -> 2) | `status = CANCELLED`, `cancelled_at` set |

The threshold is `queue_settings.max_no_shows` (default 2). Each no-show is written to `token_events` and counted on the dashboard.

## 16. Priority Logic

Priority only re-orders the **waiting** list. It never touches the token being served.

```
IT-010 SERVING          IT-011 (priority) arrives
IT-010 keeps SERVING -> IT-010 completes -> IT-011 SERVING
```
Priority can be requested by the visitor (when `allow_visitor_priority` is on for that department) or set / removed by staff (`POST /api/tokens/:id/priority`).

## 17. Transfer Logic

Staff of the token's department (or an admin) picks another department. The backend, in one transaction: closes the open service session (if it was being served), inserts a row in `token_transfers`, moves the token to the new department, sets it `WAITING` with a new sequence number (end of that queue), logs a `TRANSFERRED` event, recalculates the estimate, and refreshes both departments' daily stats. The token keeps its number (`IT-023` stays `IT-023` in the HR queue).

**Pause / Resume.** Pausing blocks *new* token generation (409) while existing tokens, calling and completing all keep working. Resume re-opens generation.

## 19. API Documentation

Base URL `http://localhost:8080`. JSON everywhere. Errors: `{"error": "message"}` with 400 / 401 / 403 / 404 / 409. Staff endpoints need `Authorization: Bearer <JWT>`.

### Public

| Method | Path | Notes |
|--------|------|-------|
| GET | `/api/health` | liveness |
| POST | `/api/auth/login` | `{"email","password"}` -> `{"token":"JWT","user":{"id":1,"name":"Admin","role":"ADMIN"}}` |
| GET | `/api/departments` | each with `status`, `waiting`, `serving`, `currently_serving[]`, `estimated_wait_seconds`, `allow_visitor_priority` |
| GET | `/api/departments/:id` | same shape, one department |
| POST | `/api/visitors` | `{"name","mobile"}` -> visitor (optional; `POST /api/tokens` can take name + mobile directly) |
| POST | `/api/tokens` | `{"department_id":1,"name":"Sohan","mobile":"9876543210","priority":false}` -> 201 token. 409 if the department is paused or the mobile already has an active token there |
| GET | `/api/tokens/:id` | token with live `queue_position`, `people_ahead`, `estimated_wait_seconds` |
| PATCH | `/api/tokens/:id/cancel` | only while `WAITING`, otherwise 409 |
| GET | `/api/tokens/:id/queue-position` | position, people ahead, estimate, `currently_serving[]`, anonymous `queue[]` (people ahead + you) |

### Staff (JWT)

| Method | Path | Notes |
|--------|------|-------|
| GET | `/api/auth/me` | current user |
| GET | `/api/dashboard` | `{"waiting","serving","completed","no_shows","average_waiting_minutes","average_service_minutes","departments":[{"id","name","code","status","waiting","serving"}]}` |
| GET | `/api/queues/:departmentId` | `{"department","serving":[...],"waiting":[... in call order ...],"completed_today","no_shows_today"}` |
| POST | `/api/queues/:departmentId/call-next` | 404 if empty, 409 if you are still serving someone |
| POST | `/api/tokens/:id/complete` | must be `SERVING` |
| POST | `/api/tokens/:id/no-show` | must be `SERVING` |
| POST | `/api/tokens/:id/transfer` | `{"department_id":3,"reason":"optional"}` - `WAITING` or `SERVING` token |
| POST | `/api/tokens/:id/priority` | `{"priority":true,"level":1}` (`priority` defaults to true) - `WAITING` token only |
| PATCH | `/api/departments/:id/pause` | |
| PATCH | `/api/departments/:id/resume` | |

Authorization: **ADMIN** may act on any department; **STAFF** only on their own (403 otherwise). Viewing queues and the dashboard is allowed for all staff.

Example:
```bash
TOKEN=$(curl -s localhost:8080/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"it.staff@smartoffice.com","password":"Staff@123"}' | sed 's/.*"token":"\([^"]*\)".*/\1/')
curl -s -X POST localhost:8080/api/queues/1/call-next -H "Authorization: Bearer $TOKEN"
```

## Design decisions and known limitations

- **Visitors have no accounts**, as specified. Anyone who knows a numeric token id can view or cancel it. For production add a per-token secret returned at creation and required on cancel.
- Live updates use **REST polling** (5 s), as the blueprint allows. SSE / WebSocket would be a later improvement.
- A visitor's tokens are remembered in the browser (token ids in local storage) for the **My Token** screen.
- Staff sessions are JWTs valid for `JWT_TTL_HOURS`; there is no refresh token or server-side revocation.
- Priority requests by visitors are on by default (`queue_settings.allow_visitor_priority`); set it to `false` per department to restrict priority to staff.
